# Design Review Tool

**Версия:** 1.0  
**Дата:** 15 сентября 2026  
**Статус:** утверждено в обсуждении; реализация в отдельном репозитории  
**Репозиторий:** `~/work/personal/design-review-tool` (SourceCraft, private)

## 1. Цель

Один self-hosted портал, в котором клиент по ссылке открывает живой HTML-дизайн из приватного git, сравнивает варианты, смотрит 390 / 768 / 1440 и оставляет треды на элементах и прямоугольниках. Комментарии не теряются при обновлении HTML. Админ заводит проекты и именные входы. Агент забирает фидбек JSON-экспортом.

Это не форк Peek и не SaaS. Каталог не переписывается в React: React — только рамка вокруг iframe.

## 2. Почему своё, а не Peek / cloud

Peek отдаёт один загруженный HTML-файл, без папки `assets/`, без A/B на одной ссылке, без пресетов вьюпорта и без git. Нужные куски всё равно писать с нуля, а модель upload/slug мешает git-пути.

Дешёвые cloud (SiteViewer Studio, PinDrop) не закрывают A/B + 390/768/1440 + интерактивный HTML из приватного репо на одной ссылке.

Источник правды для макетов — git. Источник правды для комментариев — SQLite на VDS.

## 3. Пользователи

**Админ** (ты): один пароль из конфига на VDS. Заходит на `/admin`. Создаёт проекты, пути в git, варианты, именные учётки клиента, жмёт Sync, скачивает JSON.

**Ревьюер** (клиент или ты в том же UI): учётка «Имя + пароль», заведённая админом. Открывает `/p/<slug>`, логинится, смотрит превью, пишет/отвечает/резолвит. Свободное имя при входе запрещено — автор комментария = учётка.

Несколько ревьюеров на проект: у Анны и Ивана разные пароли, один slug.

## 4. Клиентский экран

После логина одно окно:

- сверху: варианты (A/B/…), пресеты 390 / 768 / 1440, список коммитов, имя, выход;
- в центре: iframe с HTML из checkout выбранного SHA;
- сбоку: открытые треды текущего варианта.

Клик по элементу в режиме комментария ставит пин. Перетаскивание прямоугольника ставит область. Тред: тело, ответы, статус открыт/решён, reopen.

Превью, список коммитов и API комментариев без валидной сессии ревьюера не отдаются. Sync, git URL, пароли учёток — только `/admin`.

## 5. Проект и git

Инстанс держит несколько проектов.

Проект:

- человеческое имя;
- стабильный `slug` → URL `/p/<slug>`;
- git URL (SSH / HTTPS / локальный путь для тестов);
- ветка;
- список вариантов `{ key, label, gitPath }`, минимум один. Для цветочного каталога два пути в одном коммите;
- опциональный путь к SSH-ключу, иначе ключ из конфига инстанса.

Один clone на уникальный git URL. Несколько проектов могут смотреть разные папки одного репо.

**Sync в админке:** `git fetch`. История = `git log` по объединению путей вариантов, не по всему репо. По умолчанию latest. Клиент переключает SHA; A и B всегда из одного коммита. Checkout SHA по запросу, на диске не храним все версии.

`git_url` и ключ никогда не попадают в браузер.

## 6. Комментарии

Поля корневого комментария: проект, вариант, SHA на момент создания, viewport (390|768|1440), автор = reviewer id, kind `element` | `rect` | `page`, CSS-selector и/или `data-review-id`, нормализованный rect (доли документа 0–1), текст, статус `open` | `resolved`, timestamps.

Ответы: тот же тред, автор, текст, время. Resolve/reopen — на корне, не на ответе.

Список по умолчанию: все **открытые** комментарии текущего варианта, со всех SHA. SHA в карточке как «на какой версии оставили». На другой версии селектор может не найтись — тред в списке остаётся, подсветка пишет «элемент не найден».

## 7. Архитектура

Один процесс Node/TS на VDS, один открытый порт, HTTP (без TLS, пока нет домена).

- Hono: API, админка, раздача React-сборки и preview-файлов.
- SQLite: проекты, ревьюеры, сессии, комментарии.
- React (Vite): только chrome логина, рамки и панели.
- Системный `git` для fetch/log/checkout.
- Preview: `sandbox="allow-scripts allow-popups"` без `allow-same-origin`. В HTML на лету инжектится маленький `bridge.js` (файлы в git не меняем). Ассеты как есть. Cookie ревьюера `Path=/p/<slug>`, админа `Path=/admin`. Path traversal из git-пути — 403.

## 8. Данные

- `projects` — slug, title, git_url, branch, ssh_key_path nullable
- `variants` — project_id, key, label, git_path
- `reviewers` — project_id, name unique per project, password_hash, disabled
- `admin_sessions` / `reviewer_sessions` — signed HttpOnly cookie (HMAC), не JWT в localStorage
- `comments` — поля раздела 6
- `replies` — comment_id, reviewer_id, body, created_at

Пароль ревьюера после создания не читается, только сброс. Админ-пароль — bcrypt/hash в конфиге или plaintext только в локальном `.env`, не в git.

Экспорт админки: JSON всех тредов проекта (комментарии, ответы, variant, sha, viewport, selector/rect, статусы, имена авторов) для Cursor/Codex.

Backup v1: копия файла SQLite. Clone git можно перекачать.

## 9. Безопасность

- Серверная проверка имени+пароля, не «секрет в ссылке».
- Rate limit на логин.
- Ревьюер проекта A не видит проект B.
- Выключенная/удалённая учётка теряет сессию.
- HTML в iframe не читает cookie рамки.
- На IP без HTTPS пароль идёт открытым текстом — приемлемо для одного клиента на закрытом порту; перед широкой раздачей нужен домен и Caddy.

## 10. Вне объёма v1

OAuth, аккаунты админов, MCP, AI-разбор комментариев, скриншот/crop, webhook GitHub (на «просто IP» всё равно не дойдёт), публичный интернет-хостинг, переписывание HTML-каталога, Figma.

## 11. Проверки

Автотесты: логин, изоляция проектов, persist комментариев при смене SHA, resolve/reopen, тред, раздача `./assets/` без 404, path traversal, экспорт JSON.

Браузер: логин → A/B → три ширины → пин и rect → второй ревьюер видит тред → Sync нового коммита, ссылка та же, открытые треды на месте.

## 12. Критерий готового v1

Админ заводит проект на приватный репо и две папки вариантов, создаёт «Анна» и «Иван». Анна открывает `http://<ip>:<port>/p/<slug>`, входит, смотрит оба варианта на 390/768/1440, листает историю, оставляет пин и rect. Иван видит это в том же списке и резолвит. Админ скачивает JSON. HTML с фото живой, не скриншот.
