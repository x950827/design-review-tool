# Как работать с Design Review

Портал для ревью живого HTML из git: админ заводит проект, ревьюер открывает ссылку, смотрит варианты на 390 / 768 / 1440 и оставляет треды. Макет остаётся HTML в iframe. React — только рамка (логин, док, панель комментариев).

Инструкция для людей, которые ревьюят, и для агентов, которые забирают фидбек и правят макет.

## Запуск

```bash
cp .env.example .env
# ADMIN_PASSWORD и SESSION_SECRET (минимум 16 символов)
npm install
npm test
npm run build:web
npm run dev
```

Открыть `http://127.0.0.1:8787/admin`. На VDS: `HOST=0.0.0.0`, ключ к приватному репо в `GIT_SSH_KEY`. Без HTTPS пароль идёт открытым текстом.

После правок в `web/` снова `npm run build:web`. `bridge.js` читается при старте процесса — после его изменения сервер нужно перезапустить.

## Людям

### Админ

`/admin`, пароль из `ADMIN_PASSWORD`.

1. Создать проект: название, slug, git URL, ветка, пути папок вариантов A и B внутри репо (там должен быть `index.html`).
2. Нажать **Sync git** — подтянется история коммитов по этим путям.
3. Добавить именные учётки ревьюеров (имя + пароль). Свободная регистрация запрещена.
4. Отдать клиенту `/p/<slug>`. Для себя можно войти той же ссылкой: учётка **Админ** создаётся автоматически с паролем админки.

**Экспорт JSON** на карточке проекта — все треды, ответы, селекторы, rect, SHA, viewport. Это вход для агента.

### Ревью

Логин: имя учётки и пароль. Дальше одно окно.

Док снизу:

- вариант A / B;
- ширина 390 / 768 / 1440;
- коммит;
- режим: **Просмотр**, **Элемент**, **Выделить**.

Справа — открытые комментарии текущего варианта со всех SHA. Решённые из списка пропадают.

Три способа оставить комментарий:

1. **Элемент** — клик по блоку в превью. Рядом с пином всплывает карточка: селектор, Size / Color / Bg / Font / Line, текст, кнопка «Комментарий». Карточка рисуется поверх iframe и может выходить за его край.
2. **Выделить** — протянуть прямоугольник. Рядом полоска «Заметка к выделению…». Крестик возвращает в просмотр.
3. **+** в шапке панели — комментарий без привязки к блоку или рамке (`kind: page`).

Ответ пишется в карточке треда. **Resolve** закрывает корень. Клик по треду подсвечивает якорь в превью; если селектора уже нет на этой версии, будет «Элемент не найден на этой версии».

Не пишите пин и выделение в композере справа — его больше нет. Справа только список, ответы и свободный комментарий через +.

## Агентам

### Роли репозиториев

| Что | Где | Трогать? |
| --- | --- | --- |
| Рамка портала | этот репо, `web/`, `src/` | только если чините сам портал |
| Макет на ревью | git проекта (папки вариантов) | да, когда правите дизайн по комментариям |
| Комментарии | SQLite на инстансе | нет, только читать экспорт |

Каталог / лендинг **не** переписывать в React этого репо. Превью — HTML (+ CSS/JS/картинки) из checkout. В HTML на лету инжектится `src/bridge.js`, файлы в git макета не меняются.

### Забрать фидбек

С инстанса, под сессией админа:

```
GET /admin/api/projects/:id/export.json
```

Или кнопка **Экспорт JSON** в `/admin`. Внутри `{ comments, replies }`. Поля комментария, которые нужны для правки:

- `body`, `author_name`, `status` (`open` / `resolved`)
- `kind`: `element` | `rect` | `page`
- `selector` — CSS-путь или `[data-review-id="…"]`, если в макете проставлен атрибут
- `review_id` — значение `data-review-id`, если было
- `rect_x/y/w/h` — доли от размера **документа** (0–1), не пиксели вьюпорта
- `viewport` — 390, 768 или 1440: смотреть баг на этой ширине
- `variant_key` — какая папка (`a` / `b`)
- `commit_sha` — на какой версии оставили; открытые треды живут и на новых SHA

Берите **открытые**. Решённые — контекст, не to-do.

### Как чинить по kind

**element.** Найти узел по `selector`. Если селектор хрупкий (`nth-of-type`, длинная цепочка), лучше повесить стабильный `data-review-id` в макете и больше не ломать его. Спеки в UI (шрифт, цвет, размер) — подсказка с момента клика, в экспорт они не пишутся.

**rect.** Это область кадра, не элемент. Смотреть тот `viewport` и тот вариант; править то, что попало в рамку. Координаты нормализованы к scrollWidth/scrollHeight.

**page.** Замечание на страницу целиком: тон, сетка, «в целом». Якоря нет.

Ответы в `replies` склеивать с родителем по `comment_id`.

### Как проверить

После правки: коммит в репо макета → в админке портала **Sync git** → в ревью выбрать новый SHA, тот же вариант и viewport, что в комментарии. Открытые треды остаются. Если селектор жив, клик по треду должен подсветить блок.

Не считайте работу сделанной по скриншоту рамки. Нужно открыть `/p/<slug>` и пройти сценарий: пин, выделение, свободный комментарий, смена ширины, второй вариант.

### Если правите сам портал

- Chrome: `web/src/` (логин, админка, док, панель, оверлеи). Стили — `web/src/styles.css`.
- Пин-карточка и полоска выделения живут в `web/src/review/AnchorDrafts.tsx`, порталятся в `document.body`, чтобы их не резал `overflow` iframe.
- Клики по макету — `src/bridge.js` (`postMessage`: `pin` / `rect` / `focus-anchor` / `set-mode`).
- API и git: `src/app.ts`, `src/comments.ts`, `src/git.ts`. Kind `page` уже есть, не выдумывать новый.
- Не возвращать композер пина/rect в правую панель.
- Не менять auth, cookie path, SQLite-схему и sandbox-поведение превью без явной задачи.
- Копирайт интерфейса — русский, кроме технических ярлыков вроде Resolve и SHA.

Подробный продуктовый спек: `docs/superpowers/specs/2026-09-15-design-review-portal-design.md`. Где UI разошёлся со спеком (оверлеи вместо композера в панели) — верить текущему коду и этой инструкции.
